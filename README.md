# Нейроассистенты для автосалона «АвтоГрад»

Учебный проект: три нейроассистента для дилерского центра — продажи, HR, постпродажное обслуживание. Репозиторий содержит концепцию, техническую архитектуру, план реализации, журнал инженерных решений и фикстуры данных, на которых всё это проверяется.

> **Дисклеймер.** Дилер «АвтоГрад», марки Aurora / Vega / Vector, модели, цены, VIN, вакансии, имена сотрудников и клиентов, телефоны и банки-партнёры **вымышлены**. Реальные персональные данные не используются и не обрабатываются. VIN невалидны и начинаются с `TESTAG`, телефоны — в заведомо нероутируемых диапазонах.

## Три ассистента

| Ассистент | Контур | Что делает |
|---|---|---|
| **«Первый контакт»** | Продажи | Принимает входящие обращения, подбирает автомобиль из стока, квалифицирует клиента, записывает на тест-драйв |
| **«Кадровик»** | HR, два контура | Разбирает отклики, ведёт скрининг, приглашает на интервью; отвечает сотрудникам по кадровым вопросам |
| **«АвтоГрад Сервис»** | Постпродажа | Регламент ТО, запись в сервис, статус ремонта, приём претензии, условия гарантии |

## Установка и настройка

```bash
python -m pip install -r requirements.txt
cp .env.example .env
```

Дальше открыть `.env` и заполнить. Сам `.env` в репозиторий не попадает — он в `.gitignore`.

| Переменная | Зачем | Где взять |
|---|---|---|
| `OPENAI_API_KEY` | Вызов модели | Личный кабинет OpenAI |
| `AVTOGRAD_MODEL` | Модель по умолчанию | Необязательно, по умолчанию `gpt-5-mini` |
| `AVTOGRAD_CLIENT_BOT_TOKEN` | Клиентский бот: продажи, найм, сервис | @BotFather → `/newbot` |
| `AVTOGRAD_STAFF_BOT_TOKEN` | Внутренний бот: контур сотрудников | @BotFather → отдельный бот |
| `AVTOGRAD_STAFF_IDS` | Кому открыт внутренний контур | Числовые id через запятую |
| `AVTOGRAD_OPS_BOT_TOKEN` | Консоль эскалаций: передача диалога человеку | @BotFather → третий бот |
| `AVTOGRAD_OPS_IDS` | Кому приходят карточки эскалаций | Свой список, не тот, что у внутреннего |
| `AVTOGRAD_HOLD_MINUTES` | Через сколько минут молчания оператора диалог вернётся боту | По умолчанию 30 |

Пустой `AVTOGRAD_STAFF_IDS` означает «никого»: внутренний бот молча отклонит всех и запишет идентификаторы обратившихся в журнал запуска — оттуда их и добавляют.

## Запуск ботов

```bash
python tools/telegram_bots.py            # оба бота
python tools/telegram_bots.py client     # только клиентский
python tools/telegram_bots.py staff      # только внутренний
```

Long polling — белый IP, домен и сертификат не нужны, демо работает с ноутбука.

## Как поговорить с ассистентами

```bash
export OPENAI_API_KEY=...          # в PowerShell: $env:OPENAI_API_KEY="..."
python tools/chat.py sales         # диалог с ассистентом продаж
python tools/chat.py service       # сервис и постпродажа
python tools/chat.py hr            # кадры
```

Один вопрос без диалога — флагом `-m`, подробности работы (какие записи базы знаний нашлись, срабатывал ли валидатор) — флагом `-v`:

```bash
python tools/chat.py sales -m "Vega Cross есть в наличии?" -v
```

Обстановку диалога можно задавать — именно так проверяются инварианты из ADR-0004:

| Флаг | Что проверяет |
|---|---|
| `--time 23:40` | Вне рабочих часов ассистент не обещает срок в минутах, а называет ближайший рабочий интервал |
| `--stale` | При устаревании данных свыше 4 часов ассистент отказывается отвечать по наличию и статусу |
| `--owner human_owned` | Диалог ведёт сотрудник — ассистент молчит и не вмешивается |
| `--model gpt-5` | Приёмка на старшей модели вместо mini для регрессов (ADR-0005) |

## Ключевые решения

Все решения зафиксированы в [журнале](ENGINEERING_JOURNAL.md) с контекстом и обоснованием. Принятые записи не переписываются: при смене курса заводится новая со статусом «заменяет ADR-NNNN».

- **ADR-0001** — состав тройки ассистентов; F&I и внутренний диспетчер отклонены как отдельные продукты и встроены иначе
- **ADR-0002** — гибрид Python + n8n с жёсткой границей: n8n никогда не в синхронном пути ответа и не получает сырых персональных данных
- **ADR-0003** — учебный контур: каждая внешняя система за портом с фикстурной и боевой реализациями
- **ADR-0004** — инварианты диалога: протокол передачи человеку, идентичность клиента сквозь каналы, версионирование ответа, календарь работы отделов
- **ADR-0005** — OpenAI в учебном контуре, российский провайдер в боевом; правило персональных данных не ослабляется
- **ADR-0006** — порядок работ: требования ТЗ закрываются раньше демо
- **ADR-0007** — фикстуры генерируются скриптом, валидатор является критерием приёмки
- **ADR-0008** — база знаний: один факт — одна запись, ни одного числа без источника, стоп-лист как источник для кода
- **ADR-0009** — промпты: общий каркас + три роли по методу `ai-instruction-design`, классы силы правил, третий валидатор
- **ADR-0010** — запускаемый прогон собран раньше срока: он нужен этапу 3 и показывает работу ассистентов вживую

## Запуск инструментов

```bash
python tools/build_fixtures.py && python tools/validate_fixtures.py && python tools/validate_kb.py && python tools/validate_prompts.py
```

```bash
python tests/test_pii.py && python tests/test_store.py && python tools/run_golden.py && python tools/build_deliverable.py
```

Состояние базы диалогов и уборка:

```bash
python tools/store.py stats
```

Первая команда собирает `docs/knowledge-base/fixtures/` — 40 автомобилей, 10 клиентов с историей обслуживания, 12 заказ-нарядов, 6 вакансий, 20 кандидатов, часы работы отделов и график дежурств. Вторая проверяет связность данных: битые ссылки между файлами, расхождение цен с прайсом, отсутствие обязательных полей у статусов, покрытие сценариев, тестовость телефонов и отсутствие в карточках кандидатов полей, по которым нельзя отсеивать.

Третья проверяет базу знаний: обязательные поля у каждой записи, существование источников, владельца и адресата эскалации из `staff.json`, непротухшие сроки жизни, покрытие всех девяти триггеров передачи человеку.

Четвёртая проверяет системные промпты: все шесть разделов ТЗ в каждой роли, протокол передачи человеку и поведение вне рабочих часов упомянуты в каждой роли, ни одного утёкшего факта — цены, вилки дохода, телефона, даты — в тексте роли.

Фикстуры руками не правятся — источник только в `tools/build_fixtures.py`.

## Состояние

**Этап 0 закрыт** — данные и каркас: 15 фикстур, 609 проверок связности.

**Этап 1 закрыт** — слой знаний: 85 записей, 1890 проверок. 60 записей FAQ по трём отделам, классификатор на 15 типов обращений в каждом, скрипты четырёх ролей, девять триггеров эскалации с адресатом и сроком в рабочих часах, стоп-лист запрещённых формулировок с шаблонами для будущего валидатора.

**Этап 2 закрыт** — системные промпты: общий каркас (`_core.md`) и три роли — «Первый контакт», «АвтоГрад Сервис», «Кадровик». Каждая роль закрывает все шесть разделов ТЗ: название и цель, приветствие, роль и тон, пошаговые сценарии, ограничения, типовые вопросы и ответы. Правила размечены по классам силы (`ИНВАРИАНТ`, `ТРЕБОВАНИЕ`, `СПРОСИТЬ`, `ПО УМОЛЧАНИЮ`) — интенсивность формулировки не создаёт обязательности, обязательность создаёт метка.

**Ассистенты запускаются и отвечают** — минимальный горячий контур собран (`tools/chat.py`). Проверено вживую на gpt-5-mini: подбор из стока с оговоркой об оферте, отказ называть скидку, устойчивость к попытке переопределить роль, честное время ответа вне рабочих часов, отказ отвечать по устаревшим данным, молчание при чужом владении диалогом, эвакуатор раньше записи при угрозе безопасности, отказ выносить вердикт по гарантии.

**Этап 3 закрыт** — прогон и сдача: 60 эталонных диалогов (20 на ассистента, 24 конфликтных, 67 реплик), ноль расхождений. Диалоги описаны данными в `tests/golden/`, прогон выполняет `tools/run_golden.py` через то же ядро, что отвечает в Telegram. Каждая реплика проверяется по стоп-листу, запретам диалога, обязательным элементам ответа и ожидаемому режиму; суммы сверяются с базой знаний. Прогон нашёл дефекты по обе стороны — у ассистентов (ложные отчёты о действиях, служебные коды в ответе клиенту) и у самого валидатора (подстрока внутри слова, разделитель разрядов, срабатывание на собственной рекомендованной замене), разбор в ADR-0014.

**Требования ТЗ закрыты.** Итоговый документ — `docs/deliverable/avtograd-assistants.md`: оглавление, три системных промпта, база знаний трёх отделов, протокол проверки, расшифровки диалогов приложением. Собирается из исходников командой `python tools/build_deliverable.py`, руками не правится. Импорт в Google Docs: Файл → Импорт → выбрать `.md`, затем Вставка → Оглавление.

**Этап 4 идёт** — горячий контур. Сделано: хранилище диалогов (`contact` / `channel_identity` / `dialog` / `message`), персональные данные вынуты из текста сообщений в отдельную таблицу значений, сроки хранения и удаление по требованию работают командами `python tools/store.py purge` и `forget`. Версия промпта считается по содержимому, пишется в каждый ответ и обязана быть описана в `docs/prompts/CHANGELOG.md` — иначе валидатор промптов краснеет. Кэш ответов на обезличенные вопросы: версии промпта и знаний входят в ключ, поэтому правка промпта обесценивает прошлый кэш без команды сброса.

**Шлюз персональных данных закрыт** — в модель уходят плейсхолдеры, ответ разворачивается обратно: клиент видит свой VIN, а модель его не видит. Проверено прогоном: ни одного плейсхолдера в расшифровках, ни одного значения в запросе.

**Этап 4 закрыт.** Внешние системы живут за портами (`DmsPort`, `CrmPort`) с фикстурными реализациями: ядро не читает JSON напрямую, недоступность DMS воспроизводится по требованию и даёт честный ответ уровня L1 вместо выдуманного статуса. Приём сообщений вынесен в HTTP-ядро на FastAPI с дедупликацией по идентификатору сообщения канала. Владение диалогом переключается командой: сотрудник забирает переписку — ассистент замолкает со следующего сообщения, реплики клиента при этом продолжают сохраняться. Эскалация оставляет запись в `var/crm_outbox.jsonl`, поэтому «передам менеджеру» подкреплено фактом.

Провайдер модели переключается двумя переменными в `.env` (`AVTOGRAD_LLM_BASE`, `AVTOGRAD_LLM_KEY`) — у GigaChat и YandexGPT есть OpenAI-совместимый endpoint. Само обещание переносимости из ADR-0005 пока не проверено: ключей нет, проверка отнесена на этап 6.

Чего в этапе сознательно нет: RAG на pgvector. Поиск по базе знаний словарный — на 85 записях этого достаточно, а pgvector требует PostgreSQL, которого в учебном контуре нет.

**Передача человеку работает в обе стороны.** Эскалация кладёт карточку дежурному в третий бот — консоль эскалаций, отдельную от внутреннего контура: в карточке видны данные клиента, а кадровый канал таких данных носить не должен. Оператор берёт диалог кнопкой, ассистент замолкает, клиенту уходит строка о подключении человека. Дальше реплики оператора уходят клиенту в тот же чат и сохраняются в диалоге с пометкой, что отвечал человек. Возврат — командой или по таймауту: клиент не должен оставаться в тишине, если оператор отвлёкся.

Проверок без единого вызова модели — 163: ядро, шлюз ПДн, хранилище, API, консоль.

```bash
python tools/api.py
```

**Дальше** — этап 5: холодный контур на n8n через API ядра, и этап 6: намеренные отказы, метрики, приёмка.
