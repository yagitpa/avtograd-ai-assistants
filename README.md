# Нейроассистенты для автосалона «АвтоГрад»

Три диалоговых ассистента дилерского центра — продажи, сервис, кадры — и обвязка, без которой их нельзя выпускать к клиенту: детерминированный валидатор исходящих сообщений, шлюз персональных данных, передача диалога живому сотруднику и фоновые сценарии на n8n.

Учебный проект, собранный целиком: от базы знаний и системных промптов до HTTP-ядра, хранилища диалогов, консоли эскалаций и проверки поведения под отказами.

> **Дисклеймер.** Дилер «АвтоГрад», марки Aurora / Vega / Vector, модели, цены, VIN, вакансии, имена сотрудников и клиентов, телефоны и банки-партнёры **вымышлены**. Реальные персональные данные не используются. VIN невалидны и начинаются с `TESTAG`, телефоны — в нероутируемых диапазонах.

## Какие задачи решает

**Первая линия не теряет обращения.** Клиент пишет в один чат в любое время суток и получает ответ по наличию, ценам, регламенту ТО, статусу ремонта, вакансиям — из данных дилера, а не из общих слов. Вопрос, требующий человека, уходит человеку с карточкой и сроком, а не растворяется.

**Ассистент не обещает того, чего не может.** Скидку, гарантийный случай, срок ремонта и приём на работу решает сотрудник. Это не просьба к модели «будь осторожна»: формулировка с таким обещанием не уходит клиенту физически — её останавливает валидатор перед отправкой.

**Персональные данные не покидают контур.** VIN, телефон, имя и госномер заменяются плейсхолдерами до обращения к модели и разворачиваются обратно в ответе: клиент видит свой VIN, модель его не видит.

**Сотрудник забирает разговор одной кнопкой.** Ассистент замолкает, клиент остаётся в своём чате, реплики идут в обе стороны, брошенный диалог возвращается ассистенту по таймауту.

**Фоновая работа не имеет доступа к людям.** Напоминания, синхронизация стока и сводки живут в n8n и получают только номера диалогов и счётчики — того, чего они не получили, не может оказаться в их журналах.

## Как устроено

Два контура, разделённые по цене отказа.

**Горячий** — Python: приём сообщения, поиск по базе знаний, сборка контекста, вызов модели, валидатор, ответ. Здесь клиент ждёт, поэтому здесь нет ничего, что можно отложить.

**Холодный** — n8n: расписания, напоминания, сводки. Ходит только через HTTP-ядро и только за идентификаторами.

Внешние системы — DMS, CRM — живут за портами с фикстурными реализациями: ядро не читает файлы напрямую, а недоступность DMS воспроизводится по требованию.

Когда что-то ломается, клиент всё равно получает ответ: молчит DMS — ассистент говорит об этом прямо и не выдумывает статус; отказал провайдер модели — ядро идёт к резервному; отказали все — шаблонный ответ и карточка дежурному; упало само ядро — автоответ из канала. Проверяется одной командой, см. ниже.

## Стек

| Слой | Чем сделано |
|---|---|
| Ядро | Python 3.10+, стандартная библиотека |
| Модель | любой OpenAI-совместимый провайдер: OpenAI, YandexGPT; GigaChat через адаптер |
| HTTP-ядро | FastAPI + uvicorn |
| Каналы | Telegram Bot API, long polling через httpx |
| Хранилище | SQLite |
| Фоновые сценарии | n8n, сценарии лежат в репозитории как JSON |
| База знаний | Markdown с полями + JSON-фикстуры, поиск словарный |
| Проверки | самописные прогоны без фреймворков |

Зависимостей четыре: `openai`, `httpx`, `fastapi`, `uvicorn`. Сборка фикстур и все валидаторы работают на стандартной библиотеке.

Чего нет намеренно: RAG на pgvector — на 85 записях словарного поиска достаточно, а pgvector тянет за собой PostgreSQL. Библиотеки чтения `.env` — загрузчик занимает десять строк.

## Что нужно для подключения

**Обязательно:** Python 3.10 или новее и ключ провайдера модели.

**Для чата в Telegram:** три бота у [@BotFather](https://t.me/BotFather) — клиентский, внутренний и консоль эскалаций. Белый IP, домен и сертификат не нужны: long polling работает с ноутбука.

**Для фоновых сценариев:** n8n — свой или облачный, плюс ключ его API.

```bash
python -m pip install -r requirements.txt
cp .env.example .env
```

Дальше заполнить `.env`. Сам файл в репозиторий не попадает.

| Переменная | Зачем |
|---|---|
| `OPENAI_API_KEY` | ключ модели |
| `AVTOGRAD_MODEL` | модель по умолчанию, необязательно |
| `AVTOGRAD_LLM_BASE` · `AVTOGRAD_LLM_KEY` | другой провайдер: адрес и ключ вместо OpenAI |
| `AVTOGRAD_LLM_FALLBACK_BASE` · `_KEY` · `_MODEL` | резервный провайдер, уровень L2 |
| `AVTOGRAD_LLM_PROVIDER` · `GIGACHAT_*` | GigaChat: у него доступ по токену, нужен адаптер |
| `AVTOGRAD_CLIENT_BOT_TOKEN` | клиентский бот: продажи, сервис, вакансии |
| `AVTOGRAD_STAFF_BOT_TOKEN` · `AVTOGRAD_STAFF_IDS` | внутренний бот и кому он открыт |
| `AVTOGRAD_OPS_BOT_TOKEN` · `AVTOGRAD_OPS_IDS` | консоль эскалаций и кто дежурит |
| `AVTOGRAD_HOLD_MINUTES` | через сколько минут молчания оператора диалог вернётся ассистенту |
| `AVTOGRAD_API_KEY` · `AVTOGRAD_API_PORT` | доступ к HTTP-ядру и его порт |
| `AVTOGRAD_DIGEST_IDS` | кому уходит утренняя сводка |
| `N8N_BASE_URL` · `N8N_API_KEY` | инсталляция n8n для заливки сценариев |
| `AVTOGRAD_TRACE_PII` | показывать работу шлюза ПДн в журнале процесса |

Пустой список идентификаторов везде означает «никого»: внутренний бот молча отклонит всех и запишет идентификаторы обратившихся в журнал запуска — оттуда их и добавляют.

Все переменные с пояснениями — в [`.env.example`](.env.example).

## Запуск

```bash
python tools/telegram_bots.py
```

```bash
python tools/api.py
```

Поговорить с ассистентом без Telegram:

```bash
python tools/chat.py sales -m "Vega Cross есть в наличии?" -v
```

Флаг `-v` показывает, какие записи базы знаний нашлись и срабатывал ли валидатор. Обстановку диалога можно задавать: `--time 23:40` — вне рабочих часов, `--stale` — данные стока устарели, `--owner human_owned` — диалог ведёт сотрудник.

Залить фоновые сценарии в n8n:

```bash
python tools/n8n_annotate.py && python tools/n8n_push.py push
```

Сценарии заливаются выключенными — расписания включает человек, посмотрев на них.

## Проверить, что всё работает

```bash
python tools/demo_check.py
```

Предполётная проверка: ключи, ядро, токены ботов, свежесть стока, сценарии в n8n, сходимость версий промптов с работающим процессом.

```bash
python tools/failures.py
```

Восемь способов уронить систему за секунду: молчит DMS, протух сток, упал основной провайдер, упали все, ядро выбросило исключение. Ни при одном клиент не остаётся без ответа. Вызовов модели ноль — модель подменена заглушкой.

```bash
python tools/check_boundary.py
```

Читает журналы n8n и ищет там телефоны, VIN, e-mail, госномера и имена из базы. Пустой результат — доказательство границы контуров.

```bash
python tests/test_core.py && python tests/test_pii.py && python tests/test_store.py && python tests/test_api.py && python tests/test_ops.py && python tests/test_cold.py && python tests/test_failures.py && python tests/test_providers.py
```

265 проверок без единого обращения к модели.

```bash
python tools/validate_fixtures.py && python tools/validate_kb.py && python tools/validate_prompts.py
```

Ещё 4018 проверок данных: связность фикстур — битые ссылки между файлами, расхождение цен с прайсом, тестовость телефонов; база знаний — обязательные поля записей, существование источников и адресатов эскалации, непротухшие сроки жизни; системные промпты — все шесть разделов ТЗ в каждой роли и ни одного утёкшего факта в тексте роли.

Версии промптов и базы знаний:

```bash
python tools/versions.py
```

```bash
python tools/run_golden.py
```

60 эталонных диалогов через то же ядро, что отвечает в Telegram. **Обращается к модели и расходует токены.** Каждая реплика проверяется по стоп-листу, запретам диалога, обязательным элементам и ожидаемому режиму; суммы сверяются с базой знаний.

Метрики качества за период:

```bash
python tools/store.py quality 7
```

## Журнал решений

Все решения зафиксированы в [`ENGINEERING_JOURNAL.md`](ENGINEERING_JOURNAL.md) с контекстом, обоснованием и следствиями. Принятые записи не переписываются: при смене курса заводится новая со ссылкой на заменяемую.

Опорные: **ADR-0002** — граница контуров и запрет персональных данных в n8n; **ADR-0004** — инварианты диалога и протокол передачи человеку; **ADR-0005** и **ADR-0028** — переносимость между провайдерами и её пределы; **ADR-0016** — версионирование промптов по содержимому; **ADR-0020** — критерий приёмки при недетерминированной модели; **ADR-0023** — контракт о режиме ответа; **ADR-0026** — лестница деградации как исполняемая проверка.
